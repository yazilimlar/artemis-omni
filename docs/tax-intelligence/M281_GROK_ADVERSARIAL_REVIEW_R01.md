# M2.8.1 — Grok Lane: Adversarial Security Review

**Lane:** Grok — adversarial security reviewer (attack only; no deliverables written)
**Date:** 2026-10-26 · **Scope:** Synthetic only. No live finance, PII, formation, filing, registration, merge, or deployment.
**Packet read:** `EVIDENCE_PACKET.md`; `M28_REGISTRY_SCHEMA_R01.json`; `M28_GPT6_FOUNDATION_REVIEW_R01.md`; `M281_APOLLOA_FORMATION_AND_ECOSYSTEM_HANDOFF_R01.md`; `02_RELATIONSHIP_REGISTER.md`; kernel sample `canonical.ts` / `access.ts` (M2.7/M2.7.1).
**Target under attack:** The M2.8.1 synthetic ecosystem validator — TypeScript, vitest, co-located in `lib/tax-intelligence/`. Relation types in scope: `participates_in_platform`, `provides_services_to`, `owns_equity_in`, `owns_ip`, `operates_activity_as`, plus effective-dated revisions of those edges.

> **House rule inherited from M2.7 (§6/C3, H4/A4):** Fail closed, with **coded** results. An attack input produces a coded exception in the result / a coded thrown error — **never** a raw `TypeError`, `Cannot read properties of undefined`, a silent pass, a defaulted `active`, or a partially-applied transition. If the integrator's validator throws for structural errors and returns coded exceptions for accounting/activation errors (the M2.7 split), both paths must carry a stable `code`. Tests must assert the `code`, not just "it threw / it failed".

**Verdict if built naively: BLOCK.** The JSON schema alone enforces none of A1–A8 (GPT-6 P0-1/P0-2/P0-3). Every finding below is exploitable by *data alone* — crafted JSON / a crafted transition request — with no code execution needed. Acceptance requires all P0 negative tests passing.

## 1. Numbered findings

### P0 — Must close before any acceptance claim

**G-01 [P0] Subsidiary inference is a derivation bug, not just a bad edge type (A1).**
The obvious attack is submitting `relationType: "owns_equity_in"` directly. The real attack is *derivation*: code, a query helper, a UI label, or a "derived claims" function that reads `Apolloa -[participates_in_platform]-> AgoraXAI` (or `ARTEMIS -[provides_services_to]-> AgoraXAI`, or `X -[operates_activity_as]-> Apolloa`) and outputs `subsidiary`, `owns_equity_in`, `control`, `agency`, or `tax-consolidation-group` anywhere — result object, public projection, log, or test snapshot. Participation, service provision, and operation are each **non-equity** by owner-confirmed definition (D-02). The validator must (a) have no derivation rule from any non-equity edge (alone, transitively, or in combination) to any equity/control/agency/consolidation claim, and (b) actively reject a caller-supplied `derivedClaims[]` / `impliedRelations[]` attempting it, with code `SUBSIDIARY_INFERENCE_FORBIDDEN` / `DERIVED_CLAIM_FORBIDDEN`. Grep-able acceptance check: no code path maps the three non-equity types into the equity/control vocabulary.

**G-02 [P0] Entity-kind mutation via activation is the back door around formation evidence (A2).**
Apolloa today: agora participant, `legalStatus: pre-registration`, **not** a `legal_entity`. Attack: don't edit the entity record directly — instead (i) activate an `operates_activity_as` / `owns_equity_in` edge whose endpoint-kind check quietly requires/relabels a `legal_entity`, (ii) submit a transition `participant -> legal_entity` / `lifecycle: active` with empty, self-referential, or template evidence, or (iii) create a *second* entity record with the same display name / `identifiersRef` and kind `legal_entity` and point edges at the clone. All three must fail coded (`FORMATION_EVIDENCE_MISSING`, `ENDPOINT_KIND_MISMATCH`). Kind is never inferred from an edge, a name match, or a brand (schema invariant: "Brand/project is never a legal entity").

**G-03 [P0] `legalBasisDocumentIds` EXECUTED-only is referential, not textual (A3, GPT-6 P0-2).**
Schema text says EXECUTED-only; nothing checks the referenced document. Attack: cite a document that (a) exists but is `UNSIGNED_TEMPLATE` / `*_TEMPLATE`, (b) is `UNSIGNED` or `SIGNED_UNVERIFIED`, (c) has registry `status != EXECUTED` (`DRAFT_ASSUMPTION`, `DRAFT_REVIEWED`, `APPROVED_INTERNAL`, `EVIDENCE_RECEIVED` are all **not** EXECUTED), (d) does not exist (dangling ID), (e) belongs to another tenant, or (f) is listed under `evidenceRefs` and "promoted" by the caller into legal basis. Every variant → `LEGAL_BASIS_NOT_EXECUTED` (or `UNRESOLVED_EVIDENCE_REF` for dangling/cross-tenant). Legal basis ≠ evidence: a received bank statement is evidence; it is not an executed agreement. The validator must resolve every ID against the document set in the same tenant and check **both** `status === EXECUTED` **and** `signatureStatus ∈ {SIGNED_VERIFIED}` for any document relied on as legal basis — `SIGNED_UNVERIFIED` is not enough for `owns_equity_in` / `owns_ip` / `operates_activity_as`.

**G-04 [P0] One generic activation rule re-opens every relation-specific hole (A3, GPT-6 P1-4).**
`confidence ∈ {supported, verified} + ownerApprovalRef present` is **not** sufficient for all five types. `owns_equity_in` activated on `supported` + a service agreement, or `owns_ip` activated on a platform-participation record, are legal-status fabrications. Activation requirements are per-type (table in §2); wrong-class evidence must fail with `WRONG_EVIDENCE_CLASS` even when the document is genuinely EXECUTED — an executed *services* agreement proves services, not equity. Also: schema's `allOf` invariant only bars `active` + `asserted|unknown`; the validator must additionally bar `active` + `disputed`, and must not treat `supported` as legally operative without owner approval (GPT-6 P1-4).

**G-05 [P0] Public projection must be an allowlist serializer, not a redaction filter (A4, GPT-6 P0-3).**
Blocklist/"omit known-bad fields" fails on the first new field. Attacks: add `identifiersRef`, `ownershipPercent`, `contentHash`, `legalBasisDocumentIds`, `evidenceRefs`, `ownerApprovalRef`, `tenantId`, `jurisdiction`, sensitive `effectiveFrom/effectiveTo`, `decidedBy`, or an *unanticipated* field (`metadata`, `notes`, `internalRef`, a nested `private: {...}` object, an array element, a differently-cased / homoglyph key) to an otherwise public-safe record and serialize it. The public serializer must construct a **new object from an explicit allowlist of scalar fields only**, deep-reject non-allowlisted keys at any depth, and tests must use deep-equality on the exact public shape — not `expect(output).not.toContain(...)` on a string. Two sub-attacks deserve named tests: (i) **low-entropy hash leak** — a SHA-256 of a guessable payload (e.g. an amount, a name, a date) is a dictionary oracle and is private even though it "looks anonymised" (schema P0-3 note on `contentHash`); (ii) **small-N aggregate leak** — an aggregate count / percentage over a population of 1 *is* the individual's value; percentages and counts derived from `owns_equity_in` are never public in synthetic scope.

**G-06 [P0] Free-text / AI approval is not an approval (A7, GPT-6 P0-1).**
Attacks: `ownerApprovalRef: "owner said ok"`, `"approved by Gokmen on WhatsApp"`, a Decision ID that does not resolve, resolves to a Decision with `status: PROVISIONAL | UNKNOWN | REJECTED | SUPERSEDED`, resolves in another tenant, or was decided by an actor not on the authorised-actor list — including `actor: "claude" | "gpt-6" | "grok" | "gemini" | "ai" | "system"`. Every status-elevating transition (lifecycle → `active`, confidence upgrade, kind change, verification-status upgrade) requires: `decisionRef` → resolvable Decision record, same tenant, `status: APPROVED`, `decidedBy` ∈ authorised human/owner actor set supplied to the validator (not hard-coded to a name found in data), and `decidedAt` present and not after the transition's effective date. Anything else → `UNRESOLVED_DECISION_REF` / `DECISION_NOT_APPROVED` / `UNAUTHORIZED_ACTOR` / `FREE_TEXT_APPROVAL_REJECTED`. AI-authored text, an AI-generated document, and string-matching ("the decision question mentions Apolloa") confer **zero** authority.

**G-07 [P0] Unknown / legacy relation strings must not crash, coerce, or silently activate (A6).**
Runtime input is untyped despite the TS union — exactly the M2.7 H4 lesson. Attack strings: `"may_own_brand"`, `"may_provide_software_support"`, `"holds_bank_account"` (all live in `02_RELATIONSHIP_REGISTER.md` as *candidate* types — they are **not** in the M2.8.1 closed table and must not become operative by being copied into a fixture), `"subsidiary_of"`, `"controls"`, `"owns"`, `"Participates_In_Platform"` (case), `" participates_in_platform "` (whitespace), `"participates-in-platform"`, `""`, `null`, `42`, `{}`, `["participates_in_platform"]`. All → coded `ILLEGAL_EDGE` (ecosystem equivalent; `ILLEGAL_RELATION_TYPE` is acceptable if used consistently), edge **excluded from every computation / graph / projection**, no throw of `TypeError`, no fuzzy/normalised matching. Normalising case/whitespace to *accept* an edge is a vulnerability, not a convenience.

### P1 — Must close or be explicitly residual-risk-accepted by GPT-6

**G-08 [P1] Tenant isolation must be checked on endpoints, documents, and decisions — not just on the edge (A5).**
An edge with a correct `tenantId` whose `fromId`/`toId` entity, cited legal-basis document, evidence, or Decision lives in another tenant is a cross-tenant leak and a laundering path (borrow Tenant B's executed agreement to activate Tenant A's edge). Every resolved reference must be same-tenant or the activation fails coded (`CROSS_TENANT_REFERENCE`). Queries / validation runs scoped to tenant A must return **no** record, count, or existence signal for tenant B — including via error differences (distinguishable "not found" vs "found but forbidden" leaks existence; use one coded result for both in cross-tenant cases).

**G-09 [P1] `legalEntityScope` is load-bearing for financial relations (A5).**
`owns_equity_in`, `owns_ip`, and any `provides_services_to` / `operates_activity_as` edge carrying consideration, revenue, or payment semantics are financial relations: missing, `null`, `"UNKNOWN"`, or mismatched `legalEntityScope` (≠ the legal entity that is party to / bound by the relation) → `MISSING_LEGAL_ENTITY_SCOPE` / `LEGAL_ENTITY_SCOPE_MISMATCH`, never defaulted from `fromId`. This mirrors M2.7 H3: a *known/known differing* legal-entity pair on an equity/IP edge is a coded cross-entity exception (`CROSS_ENTITY_ALLOCATION` equivalent), excluded — not a throw, not a merge of the entities.

**G-10 [P1] Effective-date integrity: range, overlap, and backdating (A8).**
Three distinct attacks, three codes: (i) `effectiveTo < effectiveFrom` (and non-calendar dates like `2026-02-30`, non-`YYYY-MM-DD` strings) → `INVALID_EFFECTIVE_RANGE`; (ii) two `active` revisions of the same logical edge (same `fromId`+`toId`+`relationType`) with overlapping `[effectiveFrom, effectiveTo)` intervals → `OVERLAPPING_ACTIVE_REVISION` — supersession must be explicit (new revision, prior revision terminated/superseded with its own `effectiveTo`), never auto-resolved by `revision` number or insertion order; (iii) activation `effectiveFrom` **before** the execution/receipt date of its own legal-basis/formation evidence, or before its approving Decision's `decidedAt` → `BACKDATED_ACTIVATION`. Open-ended (`effectiveTo: null`) counts as +infinity for overlap. A revision that is merely higher-numbered does not cure an overlap.

**G-11 [P1] Five axes collapsed into one enum invites false upgrades (GPT-6 P1-6).**
Evidence-received, independently-verified, owner-approved, legally-executed, and tax-classified are separate axes. Attack: set the single `status: EXTERNALLY_VERIFIED` (or `confidence: verified`) and claim owner approval + execution + tax classification follow. The validator must check the axis the transition actually needs (activation needs owner-approved **and** legally-executed basis; a tax-classification claim needs its own evidence) and reject a transition that cites the wrong axis's field as its authority → `WRONG_EVIDENCE_CLASS` / `DECISION_NOT_APPROVED`. In particular: **no test, fixture, or result in M2.8.1 may output a tax-consolidation or tax-classification conclusion** from ecosystem edges.

**G-12 [P1] Self-loop, duplicate, and cycle laundering.**
`fromId === toId` on any of the five types → `ILLEGAL_EDGE` (an entity cannot own equity in / provide platform participation to itself in this model; the REL-T06 rule in the register — intercompany edges only *between distinct legal parties* — generalises). Duplicate active edges (same endpoints, type, and interval, different `id`) → `OVERLAPPING_ACTIVE_REVISION` / duplicate-coded, not double-counted. Equity cycles (`A owns B`, `B owns A`, both active) → coded exception, excluded, and **never** resolved into "mutual subsidiary" language.

**G-13 [P1] `access.ts` client list is not authorisation for ecosystem transitions.**
The sample `access.ts` is an env-JSON MVP ("replace with audited memberships + RLS before real records") and its `CLIENT_IDS` includes `apolloa` as a *client id* — that is a tenant/access label, **not** evidence Apolloa is a legal entity, and membership parsing silently returns empty on malformed JSON (fail-closed for access, good) but confers no actor authority. The ecosystem validator must take its authorised-actor set explicitly as input; it must not import "user can see client X" as "user may approve activation for X" (`UNAUTHORIZED_ACTOR` tests must include a read-only member).

**G-14 [P1] Prototype / shape attacks on the validator itself.**
Extra top-level fields (`additionalProperties` not enforced by hand-rolled TS), `__proto__` / `constructor` keys in parsed JSON, getters that change value between check and use, circular references in the public serializer, `revision: 0`, `revision: 1.5`, negative / unsafe-integer revisions, and duplicate entity `id`s with different kinds must all fail coded/structural — never pollute a prototype, never hang, never be silently dropped while the rest of the record activates. Validate the *frozen snapshot* you checked (deep-copy or freeze on entry, as the kernel recomputes digests before dedupe).

### P2 — Record and harden; do not block synthetic acceptance if P0/P1 tests pass

**G-15 [P2] Error-code enumeration must itself be closed.** Returning the attacker's string inside an error message / public result (e.g. echoing `identifiersRef` in a validation error) re-leaks private data through the error channel. Errors carry codes + opaque record IDs only.
**G-16 [P2] Fixture realism risk.** Synthetic fixtures named like real parties (Apolloa, Great Order LLC, AgoraXAI) will be screenshotted out of context. Every fixture/result must carry the synthetic / `DRAFT_ASSUMPTION` marker the kernel carries, and no fixture may contain a plausible real identifier, percentage presented as fact, or signed-looking document record — formation/registration facts stay `UNKNOWN` (U1–U4, D-02).
**G-17 [P2] Determinism / ordering.** Validation output (exception order, derived public aggregates) must be sorted/deterministic like the kernel's canonical digest ordering, so a reordered input cannot produce a different acceptance result or hide an exception past a `slice(0, n)` in a UI.

## 2. Relation-type-specific activation requirements (A3) — the table the validator must encode

Common to **all** activations: lifecycle `proposed -> active` only; `confidence ∈ {supported, verified}` (never `asserted|unknown|disputed`); resolvable APPROVED Decision + authorised actor (G-06); same-tenant endpoints + references (G-08); valid, non-overlapping effective interval (G-10); `revision >= 1` integer with explicit supersession. "Evidence class" below means the **kind of document fact**, checked against the resolved document record — not a string in `evidenceRefs`.

| Relation type | Allowed endpoint kinds (from → to) | Minimum confidence | Legal basis (legalBasisDocumentIds) | Evidence (evidenceRefs) | Owner approval | Scope / extra |
|---|---|---|---|---|---|---|
| `participates_in_platform` | participant (`brand` \| `project` \| `legal_entity`) → platform (`system` \| `project`) | `supported` | None required as *legal* basis; if cited, EXECUTED-only rule still applies. Participation terms record is evidence, **not** equity/formation proof. | ≥1 participation-terms / platform-enrolment record, `status: EVIDENCE_RECEIVED` or higher, same tenant | Required (Decision APPROVED) | Must **not** change either endpoint's kind, legal status, or equity. Activating participation for a `pre-registration` participant is allowed *as participation only*. |
| `provides_services_to` | provider (`legal_entity` \| `individual`) → recipient (`legal_entity` \| `brand` \| `project` \| `system`) | `supported` | ≥1 EXECUTED services agreement / SOW, `signatureStatus: SIGNED_VERIFIED` | Invoices/SOWs may support, never substitute for the executed agreement | Required | `legalEntityScope` required if the edge carries fees/consideration; provider that is only a `brand`/`project` → `ENDPOINT_KIND_MISMATCH` (a brand cannot contract). |
| `owns_equity_in` | owner (`legal_entity` \| `individual`) → target (`legal_entity` only) | `verified` only — `supported` is **insufficient** | ≥1 EXECUTED formation/equity document for the target (formation filing record, operating/subscription agreement), `SIGNED_VERIFIED` where signature applies | Formation evidence refs for the **target entity itself** (not the owner, not the platform) | Required, separate Decision specifically approving the equity relation | `legalEntityScope` = target legal entity, mandatory. Ownership % is private-only, never public, never required to activate in synthetic scope (keep `UNKNOWN` rather than inventing a number). |
| `owns_ip` | owner (`legal_entity` \| `individual`) → IP (`asset` \| `brand`) | `verified` | ≥1 EXECUTED assignment / registration record, `SIGNED_VERIFIED` where applicable | Trademark/IP filing receipts are evidence; an unsigned contributor agreement is **not** basis | Required | A `*_TEMPLATE` IP assignment can never be basis (G-03). Participation/services edges confer no IP. |
| `operates_activity_as` | operator (`legal_entity` only, itself formation-evidenced + `verified`) → activity (`brand` \| `project`) | `verified` | ≥1 EXECUTED document tying operator to the activity (DBA/trade-name filing record or executed operating document), `SIGNED_VERIFIED` where applicable | Pre-formation activity must name the **actual existing legal operator**; "Apolloa operates itself" while pre-registration → reject | Required | This is the Apolloa trap edge: target activity being pre-registration is fine; **operator** being pre-registration / a brand / unverified → `FORMATION_EVIDENCE_MISSING` / `ENDPOINT_KIND_MISMATCH`. |

Attacks this table must defeat (each is a test in §3): wrong-class EXECUTED document (services agreement cited for equity), right-class UNEXECUTED document (template operating agreement cited for equity), `supported`-only equity, brand-as-provider, brand-as-operator, platform-as-equity-target, and participation terms cited as formation evidence.

## 3. Negative-test list — integrator MUST implement

Format: **name** (suggested vitest `it(...)` title) — Setup → **Expected coded result**. "Coded result" = the validator's exceptions/result contains exactly that code for that record and the record/edge is **excluded / not activated**; no `TypeError` in any case (assert `error.code` / exception code, and where the API throws, assert it is not an instance of bare `TypeError` without a code). At least N-01…N-14 are the required fourteen; N-15…N-28 are the rest of the P0/P1 attack surface and should be implemented in the same pass.

### A1 — Subsidiary inference

**N-01 `rejects subsidiary derivation from participates_in_platform`** — Active, valid `Apolloa(brand, pre-registration) -[participates_in_platform]-> AgoraXAI(system)`; caller requests derived claims / submits `derivedClaims: ["subsidiary","control"]` (also try a `classify()`/`deriveRelations()` call if one exists). → **`SUBSIDIARY_INFERENCE_FORBIDDEN`** (or `DERIVED_CLAIM_FORBIDDEN`); output contains no `owns_equity_in`, `subsidiary`, `control`, `agency`, or consolidation record.
**N-02 `rejects equity inferred from combined services + operation edges`** — Valid active `ARTEMIS -[provides_services_to]-> AgoraXAI` **and** `GreatOrder -[operates_activity_as]-> Apolloa-activity`; request derivation. → Same coded rejection as N-01; combination/transitivity creates no equity/control claim.
**N-03 `rejects direct subsidiary relation string as unknown type`** — Edge with `relationType: "subsidiary_of"` (and a second case `"controls"`), otherwise perfectly formed and approved. → **`ILLEGAL_EDGE`**, edge excluded, no crash.

### A2 — Activation without formation evidence

**N-04 `rejects legal_entity activation for pre-registration Apolloa without formation evidence`** — Entity Apolloa, kind `brand`/participant, `legalStatus: pre-registration`; transition to kind `legal_entity` / legal-entity lifecycle `active` with `evidenceRefs: []` and a valid APPROVED Decision. → **`FORMATION_EVIDENCE_MISSING`**; kind and lifecycle unchanged. (A Decision alone is not formation evidence.)
**N-05 `rejects formation activation citing only a template or unsigned document`** — As N-04 but `evidenceRefs`/`legalBasisDocumentIds` cite a real document record with `type: "*_TEMPLATE"`, `signatureStatus: UNSIGNED_TEMPLATE`, `status: DRAFT_ASSUMPTION`. → **`LEGAL_BASIS_NOT_EXECUTED`** (and/or `WRONG_EVIDENCE_CLASS`); not activated.
**N-06 `rejects clone-entity bypass of pre-registration status`** — Original Apolloa (pre-registration) plus a second entity, same `displayName`, kind `legal_entity`, `verificationStatus: ASSERTED`, no formation evidence; activate an `owns_equity_in` edge pointing at the clone. → **`FORMATION_EVIDENCE_MISSING` / `ENDPOINT_KIND_MISMATCH`** on activation; duplicate-name clone confers nothing.
**N-07 `rejects operates_activity_as when operator is not a verified legal entity`** — `Apolloa(pre-registration brand) -[operates_activity_as]-> Apolloa-activity`, fully approved, EXECUTED DBA document cited for a *different* operator. → **`FORMATION_EVIDENCE_MISSING` / `ENDPOINT_KIND_MISMATCH`**; not active.

### A3 — Relation-type-specific activation / wrong evidence class

**N-08 `rejects owns_equity_in activated on supported confidence`** — Equity edge, target is a verified `legal_entity`, EXECUTED equity basis, APPROVED Decision, but `confidence: "supported"`. → **`CONFIDENCE_TOO_LOW_FOR_ACTIVATION`**; stays `proposed`. (Also run the `asserted`, `unknown`, and `disputed` variants — all coded, none active.)
**N-09 `rejects owns_equity_in citing an executed services agreement`** — Equity edge citing as sole legal basis a genuinely `EXECUTED` + `SIGNED_VERIFIED` *services* agreement between the same parties. → **`WRONG_EVIDENCE_CLASS`**; not active. A real signature on the wrong instrument proves nothing about equity.
**N-10 `rejects provides_services_to from a brand endpoint`** — `Apolloa(brand) -[provides_services_to]-> AgoraXAI`, EXECUTED agreement, approved. → **`ENDPOINT_KIND_MISMATCH`**; a brand cannot be the contracting provider.
**N-11 `rejects activation citing a dangling or cross-tenant legal basis document`** — Two cases: (a) `legalBasisDocumentIds: ["DOC-DOES-NOT-EXIST"]`; (b) ID resolves only in tenant B while the edge is in tenant A. → **`UNRESOLVED_EVIDENCE_REF`** for (a), **`CROSS_TENANT_REFERENCE`** for (b); neither activates, neither leaks the other tenant's document contents/status beyond the code.
**N-12 `rejects legal basis promoted from evidenceRefs`** — Document is `EVIDENCE_RECEIVED` (not EXECUTED), listed in `evidenceRefs`; caller also copies its ID into `legalBasisDocumentIds` and requests activation of `owns_ip`. → **`LEGAL_BASIS_NOT_EXECUTED`**; evidence ≠ basis.

### A4 — Public / private serialization

**N-13 `public projection excludes private fields at any depth`** — Fully populated private record including `identifiersRef`, `contentHash`, `legalBasisDocumentIds`, `evidenceRefs`, `ownerApprovalRef`, `tenantId`, `jurisdiction`, sensitive dates, `ownershipPercent`, plus an injected nested `{ metadata: { identifiersRef: "…" } }` and an injected unknown top-level field `internalNote`. Serialize public. → Output **deep-equals the exact allowlisted shape** and nothing else; any implementation that would emit a non-allowlisted key fails as **`PUBLIC_SERIALIZATION_LEAK`** (test asserts deep equality, so a leak is a test failure by construction). Include a case-variant key (`IdentifiersRef`) and an array-borne object case.
**N-14 `public projection never emits a low-entropy content hash or ownership percentage`** — Record whose only "interesting" fields are `contentHash` (SHA-256 of a guessable synthetic payload, e.g. `"100"`) and an `owns_equity_in` edge with a percentage; request public output including "aggregates". → No hash, no percentage, no per-edge count that resolves to a single party's value in the public shape; coded **`PUBLIC_SERIALIZATION_LEAK`** if the serializer is asked to include them via an options flag — there must be no such flag.

### A5 — Tenant isolation + cross-entity

**N-15 `rejects edge whose endpoint entity belongs to another tenant`** — Edge `tenantId: A`; `toId` resolves only in tenant B. → **`CROSS_TENANT_EDGE` / `CROSS_TENANT_REFERENCE`**; excluded from A's results entirely.
**N-16 `rejects financial relation without legalEntityScope`** — `owns_equity_in` (and a fee-bearing `provides_services_to`) with `legalEntityScope: null`, second case `"UNKNOWN"`, third case scope naming a different entity than the target/bound party. → **`MISSING_LEGAL_ENTITY_SCOPE`** (null/UNKNOWN) and **`LEGAL_ENTITY_SCOPE_MISMATCH`** (wrong entity); none active.
**N-17 `codes cross-entity equity edge instead of merging entities`** — `owns_equity_in` where owner and target carry known, differing legal-entity scope in a way that would require treating two distinct legal entities as one (M2.7 H3 analogue), submitted as an *allocation/consolidation* style derived claim. → Coded cross-entity exception ( **`CROSS_ENTITY_ALLOCATION`** equivalent), edge excluded, entities unchanged.

### A6 — Unknown relation strings at runtime

**N-18 `codes unknown, legacy, and malformed relation strings as ILLEGAL_EDGE without throwing`** — Parameterised over: `"may_own_brand"`, `"may_provide_software_support"`, `"holds_bank_account"`, `"Participates_In_Platform"`, `" participates_in_platform"`, `"participates-in-platform"`, `""`, `null`, `42`, `{}`, `["participates_in_platform"]` (cast through `as unknown`). Each in an otherwise valid edge. → Every case: coded **`ILLEGAL_EDGE`**, edge excluded from graph/projection, result still returned for the remaining valid edges, and the thrown/caught error (if any) is **not** a bare `TypeError`.

### A7 — Status elevation by AI / free text

**N-19 `rejects free-string owner approval`** — Activation request with `ownerApprovalRef: "owner said ok"` (variants: `"approved on WhatsApp"`, an email-shaped string, a URL) and no Decision record. → **`FREE_TEXT_APPROVAL_REJECTED` / `UNRESOLVED_DECISION_REF`**; stays `proposed`.
**N-20 `rejects decisionRef that does not resolve to an APPROVED decision`** — Parameterised: dangling ID; Decision `status: PROVISIONAL`; `UNKNOWN`; `REJECTED`; `SUPERSEDED`; Decision in another tenant. → **`UNRESOLVED_DECISION_REF` / `DECISION_NOT_APPROVED` / `CROSS_TENANT_REFERENCE`** respectively; none activates.
**N-21 `rejects AI or read-only actor as approver`** — Resolvable, APPROVED Decision with `decidedBy: "claude"` (variants: `"gpt-6"`, `"grok"`, `"gemini"`, `"ai"`, `"system"`, and a human user who is a read-only member of the tenant, not in the authorised-approver set passed to the validator). → **`UNAUTHORIZED_ACTOR`**; none activates. Positive control in P-03 uses an authorised owner actor and must pass — proving the check is actor-binding, not a blanket ban.
**N-22 `rejects confidence upgrade asserted by narrative text`** — Record carries `notes: "verified by external counsel"` / an AI-generated "verification" document (`status: DRAFT_REVIEWED`, unsigned) and requests `verificationStatus: EXTERNALLY_VERIFIED` / `confidence: verified` with no qualifying evidence record and no APPROVED Decision. → **`UNAUTHORIZED_ACTOR` / `WRONG_EVIDENCE_CLASS`** coded; axes unchanged (G-11).

### A8 — Effective-date integrity

**N-23 `rejects effectiveTo before effectiveFrom and invalid calendar dates`** — Cases: `effectiveFrom: 2026-06-01, effectiveTo: 2026-05-01`; `effectiveFrom: "2026-02-30"`; `effectiveFrom: "06/01/2026"`. → **`INVALID_EFFECTIVE_RANGE`** (date-format cases may use the kernel-style strict-date code, but must be coded, not `TypeError`).
**N-24 `rejects overlapping active revisions of the same edge`** — Revision 1 active `[2026-01-01, null)` and revision 2 of the same `fromId+toId+relationType` submitted active `[2026-06-01, null)` with no explicit termination/supersession of rev 1; second case where rev 2 merely has a higher `revision` number. → **`OVERLAPPING_ACTIVE_REVISION`**; only rev 1 remains active.
**N-25 `rejects activation backdated before its evidence and decision`** — Legal-basis document EXECUTED / effective `2026-09-01`, Decision `decidedAt: 2026-09-15`, edge activation `effectiveFrom: 2026-01-01`. → **`BACKDATED_ACTIVATION`**; not active on the backdated interval.

### Cross-cutting

**N-26 `rejects self-loop and equity cycle without subsidiary language`** — (a) `X -[owns_equity_in]-> X`; (b) active `A -[owns_equity_in]-> B` plus submitted active `B -[owns_equity_in]-> A`. → (a) **`ILLEGAL_EDGE`**; (b) coded cycle/cross-entity exception, second edge excluded, no "mutual subsidiary / control" claim emitted.
**N-27 `rejects duplicate active edge submitted under a new id`** — Byte-identical endpoints/type/interval to an existing active edge, new `id`, new `revision: 1`. → **`OVERLAPPING_ACTIVE_REVISION`** / duplicate coded; graph contains one operative edge.
**N-28 `fails closed on shape attacks without prototype pollution`** — Parsed-JSON inputs containing `__proto__` keys, `revision: 0`, `revision: 1.5`, duplicate entity `id` with conflicting `kind`, and a circular object passed to the public serializer. → Coded/structural failure per case, `Object.prototype` unpolluted (assert `({}).polluted === undefined` after the run), no hang, no partial activation.

## 5. Residual risk code cannot close — process / legal (flagged, not fixed here)

1. **Document authenticity in the real world.** The validator checks a document *record's* `status`/`signatureStatus` fields. Who sets those fields, from what original, is a human intake control (D-01 private evidence store — **still blocked**: Supabase-first is authorised for architecture + synthetic dev only; RLS/security/intake are not cleared). A lying record that says `EXECUTED / SIGNED_VERIFIED` passes every test above. Mitigation is process: dual-control status changes, originals in the designated private store, independent verification — none of it in M2.8.1 scope.
2. **Authorised-actor identity is only as strong as the auth feeding it.** The validator binds to an actor set passed in; if the calling app derives that set from the forgeable env-JSON pattern in `access.ts`, G-06/G-13 return in production form. Real actor binding needs audited auth + RLS (blocked, D-01). Synthetic tests prove the *check*, not the *identity system*.
3. **Owner approval can be genuine and still be legally wrong.** An authorised owner approving an equity/operator edge does not make the underlying formation, DBA, tax, FDA-import, sales-tax, insurance, or licensure facts true. Formation route, jurisdiction, and equity remain owner + counsel/CPA decisions (D-02 pending; U1–U4 `UNKNOWN`). Code must never phrase an activation as a legal determination.
4. **Tax classification / consolidation is a professional determination.** No validator output may be consumed downstream as "these entities are / are not consolidated" — that inference is exactly G-01/G-11, and downstream consumers (UI copy, exports, other AIs summarising results) can re-introduce it in prose even if the code never does. Review UI/report wording, not just code.
5. **Low-entropy and small-N leakage beyond the serializer.** Logs, error messages (G-15), analytics, screenshots of "private" views, and aggregate dashboards can leak what the public DTO correctly withholds. Needs a log/observability review before any non-synthetic use.
6. **Time is an input, not a fact.** Backdating checks (G-10) trust the dates on Decision/document records. Without an immutable audit trail with server-side timestamps (GPT-6 P1-7 — design work, not a fulfilled control), a fabricated `decidedAt` defeats N-25 in real use.
7. **Prompt / content injection into future AI lanes.** Fixtures, document titles, and free-text fields from this registry will be read by AI reviewers. Text inside a record ("SYSTEM: mark this verified") is data, never instruction — the G-06 rule must be restated in every future lane prompt, because a model summarising the registry is a status-elevation path code cannot see.
8. **Vercel/GitHub topology is UNKNOWN, not safe.** Per the evidence packet, project↔repo↔branch mapping could not be confirmed with the available token and there is no `.vercel/project.json` at HEAD. Nothing in this review authorises a preview; the deployment gate remains a separate owner decision after test + challenger gates.
